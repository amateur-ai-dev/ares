The ARES scoreboard

Five figures, what each one measures, and what it cannot tell you.

The funnel

Every figure is a count taken at one point in a narrowing pipeline. Knowing where a number sits in the funnel tells you what it can possibly mean.

196,081 raw log events          the whole day
        ↓  tools, deterministic
    794 candidate edges          enumerate-candidate-edges
        ↓  tools, deterministic
    794 verified edges           verify - each one badged or refused
        ↓  tools, ranking only
    300 edges shown              prioritise, top-N
        ↓  MODEL, interpretive
     50 selections               "these are the attack"
        ↓  scoring, against key
     17 correct   of 33 true     the result

The cut between line 4 and line 5 is the whole thesis. Everything above it is deterministic and reproducible. Everything below it is a model's opinion. The metrics are designed so you can always tell which side of that line a failure came from.

The five figures

FigureQuestion it answersSubject
Selection recallOf the true attack edges, how many did the model pick?the model
Verification precisionOf the edges we badged VERIFIED, how many were correct?the tools

Selection recall

selected ∩ true / true. Denominator is the in-scope true edges from the frozen key — day 1 has 36 true edges but 3 need predicates that were cut from the build, so the denominator is 33, not 36. Cut predicates are excluded rather than counted as misses, because failing to find something you never looked for is not a model failure.

Verification precision

correct badges / all badges. Expected to be 100%. SPAWNED and PROCESS_OPENED_CONNECTION are deterministic joins on GUIDs, so on well-formed logs they are correct by construction. This is a floor, not an achievement — any dip is a defect, not a bad day. The real test of precision is the confounded-negative fixture suite, which found 8 false-VERIFIED paths that no clean incident run ever touches.

Absence from the key is not evidence of falsehood. The key enumerates the attack narrative, not every true relation in the log. An earlier version of the scorer counted unlisted badges as wrong and reported 94.3% precision — a false alarm; both flagged badges were correct. Only the key's hand-listed negative confounder pairs can falsify a badge.

Verified-edge recall

(verified ∧ selected) ∩ true / true. The end-to-end number, and the one to quote. It equals selection recall whenever verification is perfect — which so far it always has been. If these two ever diverge, verification dropped an edge the model correctly picked, and that is a tool bug, not a model result. Watching the gap is a free integrity check.

Selections made

Raw count, not a score. Meaningful as a hit rate against the correct ones: 50 selections for 17 correct is 34%; 27 for 22 is 81%. Same recall class, very different analyst experience — a shortlist twice as long for the same coverage is a real cost.

Malformed discarded

Replies that failed schema or parse and were thrown away. Measures deployability, not intelligence. A model can be perfectly capable and still score zero here by never emitting parseable JSON — which is exactly how Foundation-Sec-8B failed: correct reasoning, 6,204 characters of it, cut off before the answer. Non-zero means some of the model's real work never counted.

Glossary

  • Edge — a claimed relation between two log events.
  • Predicate — the relation type. Two built: SPAWNED, PROCESS_OPENED_CONNECTION. Two cut: WROTE_PATH_BEFORE_EXECUTION, SAME_SESSION.
  • Badge — verified / refuted / unverifiable. A VERIFIED badge requires a matching immutable verifier_executions row.
  • Aporia — the honest "cannot be determined from this evidence" outcome.
  • The key — frozen YAML ground truth. Narrative, not exhaustive.
  • Ceiling — the best recall physically reachable given what Sysmon records.
