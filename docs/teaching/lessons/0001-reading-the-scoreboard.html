Lesson 0001 · ~8 minutes

Reading the scoreboard

One win: read a raw ARES run block cold and say, in order, what happened — and which number is the headline.

Here is a real block your tool printed today. Day 1, local arm, qwen2.5-7b, batched 25.

Run counts: edges-enumerated=794, edges-verified=794, verified-edges-shown=300,
            selections=50, refuted=0, aporias=0, discarded-as-malformed=7
Selection recall:        51.5% (17/33)
Verification precision: 100.0% (33/33)
Verified-edge recall:    51.5% (17/33)

Most people read that top to bottom and land on 100%. That is the wrong number to be impressed by, and knowing why is the whole lesson.

1. The two jobs

ARES splits work between two very different workers.

WorkerJobCan it be wrong?
ToolsFind every candidate relation; prove or refuse each oneOnly via a bug
ModelDecide which proven relations are the attackConstantly. That is the job

The tools answer "did A spawn B?" — a GUID match, deterministic, the same answer every run forever. The model answers "does that matter?" — judgement, no ground truth in the log itself.

Keystone. Verification precision measures the tools. Recall measures the model. They have different subjects, so they are not trading off against each other. Reading them as a single "accuracy" is the mistake to never make in front of a judge.

2. Why 100% is unimpressive

SPAWNED is: does event B's ParentProcessGuid equal event A's ProcessGuid, on the same host? That is string equality. It cannot be 97% right on well-formed logs. It is right, or the code is broken.

So 100% is a floor you must clear, not a peak you reached. The honest sentence is: "precision is 100% because verification is deterministic — that is expected, and a dip would mean a defect. The real precision test is the fixture suite, which found 8 false-VERIFIED paths a clean run never hits."

That answer is stronger than claiming 100% accuracy, because it shows you know what your own number is worth.

3. Why 51.5% is the result

33 is the denominator: day 1's key has 36 true edges, 3 need predicates cut from the build, so 33 were findable. The model found 17.

Against a measured ceiling of 78% — the best any selector could do given what Sysmon actually records — and a target band of 50–60% set before any run. So 51.5% clears the bar, at its floor. That is the number that took work.

4. The trap in the two recalls

Selection recall and verified-edge recall are both 51.5%. Not a typo, and not redundancy — it is a live integrity check.

  • Selection recall — true edges the model picked.
  • Verified-edge recall — true edges the model picked and the tools had verified.

The second can never exceed the first. When they are equal, verification dropped nothing the model got right. If they ever diverge, that is a tool bug, not a model result — and you would chase it in the verifier, not the prompt.

5. The two counts that are not scores

selections=50 and discarded-as-malformed=7 are diagnostics, and they are where the local-vs-frontier story really lives.

Day 1RecallSelectionsHit rate
Frontier, single-shot66.7%2781%
Local, batched 2551.5%5034%

Local is not just missing more — it is guessing far more. Nearly twice the shortlist for two-thirds the coverage. Recall alone hides that; the analyst feels it immediately.

And discarded-as-malformed=7 across 12 batches means seven model replies were unusable as data. That is a deployability number, not an intelligence one — real work the model did that never counted.

Check yourself

Answer from memory before scrolling back. Retrieval is what makes it stick — recognising the answer in the text above does not.

1. Verification precision drops to 96%. What does that most likely mean?

Precision measures the tools, and the tools are deterministic joins. They do not degrade gracefully — they are correct or broken. A dip is a defect to hunt, never an off day.

2. Selection recall is 51.5% but verified-edge recall is 42.4%. Where do you look first?

Verified-edge recall can never exceed selection recall. A gap means edges the model correctly picked were not verified — the tools lost them. That is a verifier bug.

3. A judge asks: "so your verification is 100% accurate?" Best answer?

Claiming it as an achievement oversells; disowning it undersells. Naming it as an expected floor — with the fixture suite as the real test — is both honest and stronger.

4. Day 2's denominator is 18, not 33. Why?

In-scope means findable with the predicates that exist. Cut predicates are excluded from the denominator rather than counted as misses — you cannot fail to find what you never looked for.
